# 0.1.1 更新链路任务计划

## 一、目标

以已经完成构建的 `v0.1.0` 为升级起点，完成一次可重复的 Windows 自动更新闭环，并改善更新检查失败时的用户提示。

本版本不进入 0.2 陪伴行为引擎，不增加自动检查或强制更新，也不调整 Tauri 更新密钥和 Windows Authenticode 方案。

## 二、任务状态

| 编号  | 任务                     | 状态   | 验收标准                                                                 |
| ----- | ------------------------ | ------ | ------------------------------------------------------------------------ |
| UP-01 | 正式发布 v0.1.0          | 待完成 | Windows 安装验收通过，草稿 Release 发布，`latest.json` 可公开访问        |
| UP-02 | 建立 v0.1.1 版本基线     | 待开始 | 前端包、Rust crate 和锁文件中的应用版本统一为 `0.1.1`                    |
| UP-03 | 改善更新检查失败提示     | 待开始 | 网络或远端清单异常时显示本地化提示，不直接展示插件原始英文错误           |
| UP-04 | 完成本地发布前验证       | 待开始 | ESLint、前端构建、Rust 格式和 workspace check 通过，Windows 实机启动正常 |
| UP-05 | 构建 v0.1.1 草稿 Release | 待开始 | GitHub Actions 生成 Windows 安装包、`.sig` 和 `latest.json`              |
| UP-06 | 验证 v0.1.0 到 v0.1.1    | 阻塞   | 已安装的 v0.1.0 能发现、下载、验证、安装 v0.1.1，并在重启后显示新版本    |

状态取值：`待开始`、`进行中`、`已完成`、`阻塞`。

UP-06 当前被 UP-01 阻塞：公开 Release API 尚未发现 `v0.1.0`，草稿版本不能作为 `releases/latest` 更新源。

## 三、实施顺序

1. 完成并发布 `v0.1.0`，保留一台已安装 `v0.1.0` 的 Windows 验收环境。
2. 将开发分支版本统一提升到 `0.1.1`。
3. 将更新检查失败提示改为本地化、可理解且不暴露底层异常的文案。
4. 完成静态检查、生产构建和 Windows 实际启动验证。
5. 从稳定分支创建签名标签并生成 `v0.1.1` 草稿 Release。
6. 使用已安装的 `v0.1.0` 执行完整更新，核对下载地址、签名、安装和重启结果。
7. 验收通过后发布 `v0.1.1`，并回写本计划的任务状态与验证证据。

## 四、产品与安全边界

- 继续只允许用户主动点击“检查更新”，不在启动时自动请求更新服务。
- 更新失败不得阻塞应用启动、桌面陪伴和本地设置功能。
- 不在界面、日志、提交或文档中输出更新私钥、密码和 Secrets 内容。
- 不关闭签名校验来绕过更新失败。
- 不将草稿 Release 描述为已正式发布，也不把未执行的升级验收标记为通过。

## 五、完成定义

- `v0.1.0` 与 `v0.1.1` 均为可公开访问的正式 Release。
- 从 `v0.1.0` 到 `v0.1.1` 的 Windows 自动更新全流程通过。
- 更新检查在成功、无更新和远端异常三种情况下都有明确结果。
- 任务状态、验证命令、遗留风险和关键 Release 地址已回写本文档。
