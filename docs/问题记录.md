### WIN-01 开发实例弹出 CrashSender 错误

#### 现象

执行 `corepack pnpm tauri dev` 测试 Windows 开发实例期间，系统曾弹出以下对话框：

```text
labu-loom has stopped working
Error launching CrashSender.exe
```

当时主窗口和自动打开的 Microsoft Edge DevTools 仍可见。此现象只出现一次，后续使用相同命令重新启动，并从终端停止开发实例时未再次复现。

#### 已确认事实

- labu-loom 仓库、依赖配置和构建产物中没有 `CrashSender.exe`、CrashRpt 初始化代码或对应调用。
- Windows 开发实例会被微信输入法加载以下腾讯签名模块：
  - `wetype_tip_core.dll`，版本 `2.0.0.27`。
  - `CrashRpt1500.dll`，版本 `1.5.0.0`。
- `CrashRpt1500.dll` 位于微信输入法的 `WetypeCore_2.0.0.27\x64` 目录；配套的 `CrashSender1500.exe` 位于另一个 `2.0.0.27` 目录。
- 上述 DLL 和 EXE 的腾讯数字签名有效；Microsoft Defender 没有返回与这些文件有关的隔离记录。
- Windows Application 事件、可靠性记录和本地目录中没有找到本次 labu-loom 异常的事件或 dump。
- 应用日志没有 Rust panic 或明确的业务异常；重新运行时主进程正常响应。
- DevTools 由 debug 构建中的 `debug_assertions` 条件代码主动打开，不属于故障；正式 release 构建不会自动打开。

#### 排查结论

弹窗由微信输入法注入到 `labu-loom.exe` 的 CrashRpt 组件生成，不是 labu-loom 主动启动的程序。CrashRpt 在认为宿主进程异常时尝试启动其报告发送程序，但该次启动失败，因此显示了二次错误提示。

由于报告发送程序没有成功运行，也没有留下 Windows 事件或 dump，目前只能确认弹窗来源，不能从现有证据确定最初触发 CrashRpt 的异常调用栈。微信输入法模块与开发实例退出过程之间的一次偶发冲突是合理推断，但不作为已确认根因。

#### 当前处理

- 该问题暂不阻塞 `0.3.7`，项目侧不为外部注入模块增加规避性代码。
- 后续开发测试若再次出现，先切换到微软拼音并重复相同步骤；如果不再出现，可进一步确认微信输入法是必要触发条件。
- 若关闭微信输入法后仍能复现，应为 `labu-loom.exe` 启用仅限本机的崩溃转储，再根据异常代码和调用栈判断是否存在项目自身的原生层缺陷。
- 可独立尝试更新或修复微信输入法，但不得把复制、替换第三方 CrashRpt 文件纳入项目安装流程。

#### 版本复盘关注点

- 实机安装 `0.3.7` 后分别在微软拼音和微信输入法环境下观察启动、打开偏好设置、输入响应和退出过程。
- 若只在 debug 构建出现，应重点比较 DevTools 打开和终端强制停止路径。
- 若 release 安装包也出现，应保留发生时间、输入法状态、操作步骤和 dump；不要仅依据 `CrashSender.exe` 文案判断为 WebView2 或 labu-loom 更新模块故障。
