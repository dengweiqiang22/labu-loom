# labu-loom 开发规范

## 一、适用范围

本文档约定 labu-loom 的本地开发、分支使用、代码修改、验证和 Git 提交方式。项目规模以个人持续开发为主，规则应保证可追溯性，但不引入不必要的流程负担。

## 二、技术栈

- 前端：Vue 3、TypeScript、Vite、Pinia、PixiJS、Live2D
- 桌面运行时：Tauri 2
- 原生层：Rust
- 包管理器：pnpm
- 首要平台：Windows

## 三、本地开发

### 3.1 安装依赖

```powershell
corepack pnpm install --frozen-lockfile
```

### 3.2 启动开发模式

```powershell
corepack pnpm tauri dev
```

### 3.3 退出开发模式

Windows 调试实例应按以下顺序退出：

1. 从 labu-loom 托盘菜单正常退出应用。
2. 确认 `labu-loom.exe` 进程已经结束。
3. 最后在终端按 `Ctrl+C` 停止 Vite 和 Tauri 开发服务。

不要在 `labu-loom.exe` 仍运行时直接使用 `Ctrl+C` 强制终止整个开发进程树。微信输入法等第三方原生模块可能把控制台终止误判为宿主崩溃，并弹出自身的崩溃上报错误。无法正常退出时，应记录当时操作和进程状态，不把强制终止结果作为应用正常退出验收。

### 3.4 前端构建

```powershell
corepack pnpm build
```

### 3.5 Rust 检查

```powershell
cargo fmt --all -- --check
cargo check --workspace --locked
```

需要提高发布前检查强度时再执行：

```powershell
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

## 四、分支约定

项目长期保留三个分支：

### 4.1 `dev`

- 默认日常开发分支。
- 功能、修复、重构和文档更新通常直接提交到此分支。
- 大型且不确定的实验可以创建临时分支，完成后合并并删除。

### 4.2 `main`

- 稳定主分支。
- 只在阶段目标完成并验证后从 `dev` 更新。
- `main` 不承担日常开发。

推荐使用快进合并，避免无意义的合并提交：

```powershell
git switch main
git merge --ff-only dev
```

### 4.3 `backup`

- 保存源项目基线。
- 不进行日常提交。
- 不随 `dev` 或 `main` 自动更新。
- 只有在明确决定刷新源项目备份时才允许移动。

## 五、代码修改原则

- 一个修改只解决一个清晰问题。
- 不把功能开发、无关重构和依赖升级混在同一个提交中。
- 修改公开行为时同步更新相关中文文档。
- 平台专属实现应与公共业务逻辑分离。
- 数据结构变化必须设计版本号和迁移路径。
- 输入监听和高频事件处理必须考虑停止、失败恢复、限频和资源释放。
- 不通过吞掉错误维持表面运行；可恢复错误应进入日志或可观察状态。

## 六、验证要求

### 6.1 文档变更

- 检查标题层级、内部链接和规则一致性。
- 如果只修改文档，可以不运行应用构建，但提交正文必须说明。

### 6.2 TypeScript、Vue 或样式变更

- 执行 ESLint 检查。
- 执行 `corepack pnpm build`。
- 涉及交互和窗口行为时，执行 `corepack pnpm tauri dev` 手动验证。

### 6.3 Rust 变更

- 执行 `cargo fmt --all -- --check`。
- 执行 `cargo check --workspace --locked`。
- 涉及输入监听、系统权限或窗口插件时进行 Windows 实际运行验证。

### 6.4 数据与记忆变更

- 检查旧数据迁移。
- 检查清除和重置流程。
- 确认没有持久化禁止记录的数据。
- 验证日、周、月聚合边界。

## 七、Git 提交规范

### 7.1 基本格式

提交信息采用 Conventional Commits，并使用带正文的结构：

```text
<类型>(<范围>): <一句话中文标题>

变更：
- 具体完成事项
- 具体调整内容

验证：
- 简要说明实际验证结论
```

标题和正文之间必须保留一个空行。

存在兼容性、数据迁移、隐私、性能或明显用户体验影响时，按需追加：

```text
影响：
- 具体影响及必要说明
```

### 7.2 类型

| 类型       | 用途                       |
| ---------- | -------------------------- |
| `feat`     | 新功能或用户可感知的新行为 |
| `fix`      | 缺陷修复                   |
| `refactor` | 不改变既有功能的代码重构   |
| `perf`     | 性能优化                   |
| `docs`     | 文档变更                   |
| `test`     | 测试代码                   |
| `build`    | 构建系统、打包或依赖配置   |
| `ci`       | CI/CD 配置                 |
| `chore`    | 其他工程维护               |
| `style`    | 纯格式调整                 |
| `revert`   | 撤销已有提交               |

### 7.3 范围

范围可选。优先使用少量稳定名称：

- `app`
- `input`
- `behavior`
- `memory`
- `model`
- `window`
- `ui`
- `build`
- `release`
- `docs`

不要为了每个目录或组件新增范围。

### 7.4 标题

- 类型和范围使用英文，说明使用中文。
- 使用动词描述最终结果。
- 不超过七十二个字符。
- 结尾不加句号。
- 不使用“修改代码”“更新内容”“处理问题”等模糊标题。

正确示例：

```text
feat(behavior): 增加陪伴模式行为调度
fix(input): 修复高回报率鼠标导致的动作抖动
docs(product): 补充记忆数据保留规则
chore(build): 配置 pnpm 构建脚本权限
```

### 7.5 正文

`变更`和`验证`为必填部分，`原因`、`影响`和`关联`按需填写。

- `原因`：缺陷修复和重要重构建议填写。
- `变更`：记录最终完成的具体事项，不记录无意义的操作流水。
- `验证`：简要记录实际验证结论，可以合并同类检查，不要求逐条罗列全部命令；未运行时说明原因。
- `影响`：仅在存在兼容性、迁移、隐私、性能或明显用户体验影响时填写。
- `关联`：填写相关 Issue、版本计划或设计文档。

正文每个细项使用 `-`，命令和代码标识使用反引号。不得包含密钥、本机绝对路径和隐私数据。

### 7.6 提交粒度

- 一个提交只完成一个逻辑目标。
- 功能代码和对应测试放在同一提交。
- 配置变更不要与无关业务功能混合。
- 重构和新功能尽量拆分。
- 自动生成文件与其来源变更一起提交。
- 不提交临时日志、本地缓存和调试数据。

### 7.7 破坏性变更

涉及存储格式、模型协议或公开接口不兼容时，在类型或范围后增加 `!`：

```text
feat(memory)!: 调整关系记忆存储结构

变更：
- 将记忆结构升级为 schemaVersion 2
- 增加旧版数据迁移流程

验证：
- 通过版本1到版本2迁移测试
- 验证全新安装和旧数据升级

影响：
- 旧版记忆数据必须完成迁移后才能读取

BREAKING CHANGE: 旧版记忆数据需要迁移到 schemaVersion 2
```

### 7.8 完整示例

```text
fix(input): 修复高回报率鼠标导致的宠物抖动

原因：
- 鼠标移动事件逐条发送到前端
- 高频事件积压后造成渲染参数快速波动

变更：
- 合并短时间内的鼠标移动事件
- 限制事件发送频率
- 保留最后一次鼠标位置

验证：
- 完成1000Hz鼠标移动测试
- `corepack pnpm build` 通过
- `cargo check --workspace --locked` 通过

影响：
- 不记录或持久化鼠标轨迹
- 降低高回报率鼠标下的CPU占用
```

纯文档提交示例：

```text
docs(product): 新增产品规划

变更：
- 记录桌面陪伴宠物的产品定位
- 确定选择式互动和长期记忆方向
- 明确键鼠数据与隐私边界
- 制定0.1至0.5版本路线

验证：
- 已检查文档结构和内部约定
- 未运行代码测试，仅修改文档
```

### 7.9 查看项目进度

Git log 用于记录已经完成的工作，未来计划仍以产品规划为准。

查看包含正文的提交记录：

```powershell
git log --date=short --pretty=format:"%h %ad %s%n%b"
```

## 八、发布约定

- 版本号采用语义化版本。
- `1.0.0` 是首个正式稳定版本；在此之前使用 `0.x.y` 版本。
- 正式版前，较大的功能或阶段性改动递增次版本号，例如 `0.1.x` 升级为 `0.2.0`。
- 兼容性 Bug 修复递增修订号，例如 `0.1.1` 升级为 `0.1.2`。
- 每次准备交付或发布的功能改动、Bug 修复都必须同步更新版本号；纯文档和不影响产物的工程维护可以不提升版本。
- 稳定版本在 `main` 创建 `vX.Y.Z` tag。
- 发布提交使用 `chore(release): vX.Y.Z`。
- 发布前必须完成前端构建、Rust 检查和 Windows 实际启动验证。
- 不在开发分支生成正式发布产物。
